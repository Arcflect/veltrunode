# [ADR-0001] アーキテクチャ設計の基本方針

* **ステータス (Status)**: 承認 (Accepted)
* **作成日 (Date)**: 2026-07-29
* **起票者/著者 (Authors)**: @hirontan
* **関連Issue/PR (Related Issue/PR)**: #11

## コンテキスト (Context)

Veltrunode は AWS 上でのサーバーレスデプロイおよびリソース構築を直感的かつ強固に行うためのRuby製フレームワーク・ツールです。
プロジェクトの初期段階から信頼性、トレーサビリティ、法的安全性を確保するため、設計意思決定の指針となるアーキテクチャ設計の基本方針を定義する必要があります。
特に、以下の要素がコンテキストとして存在します：

- **クリーンルームポリシーの徹底**: 他の既存フレームワークやツールのコード・ドキュメント・内部構造を模倣・盗用せず、完全独立して設計すること（[docs/15-clean-room-and-ip-policy.md](../15-clean-room-and-ip-policy.md)）。
- **ガバナンスと透明性**: 主要な設計変更理由や決定過程をすべて記録し、将来のメンテナーやコントリビューターが経緯を追えるようにすること（[docs/16-release-and-governance.md](../16-release-and-governance.md)）。
- **AWSネイティブ仕様への準拠**: 独自仕様の乱用を避け、CloudFormation、EventBridge Scheduler、Lambda、EFSなどのパブリックな仕様に準拠した設計を行うこと。

## 決定事項 (Decision)

Veltrunode のアーキテクチャ設計および今後の機能拡張において、以下の基本方針を遵守します。

1. **クリーンルーム開発と知的財産保護の最優先**
   - ソースコード、DSL構文、内部Lifecycle契約、エラーメッセージ等に至るまで、既存他プロジェクトからの機械的移植やコピーを固く禁止する。
   - すべての機能設計は AWS 公式ドキュメントおよびパブリック仕様、独自に整理されたユーザーニーズに基づいて行う。

2. **AWSパブリック仕様・CloudFormation構造に即した宣言的コンパイル**
   - 内部抽象化層から AWS リソース定義への変換は、CloudFormation の公開仕様にダイレクトかつ透明にマッピングされる設計とする。
   - 非標準な独自インフラ状態管理に依存せず、生成物および展開プロセスの決定性を保証する。

3. **モジュール性と関心の分離（Separation of Concerns）**
   - DSL解析、構造検証、CloudFormationテンプレートコンパイル、AWS API通信（Inspector/Deployer）などの責務を明確に分離する。
   - パッケージング（Build & Packaging）や診断（Diagnostics）の各機能を疎結合に保つ。

4. **意思決定のトレーサビリティ担保 (ADRの義務化)**
   - アーキテクチャに大きな影響を与える設計変更、DSL仕様変更、セキュリティに関する決定については、すべて ADR（`docs/adr/`）を起票・共有し、承認を得てから実装に進む。

## 代替案 (Alternatives)

- **代替案 A: 既存のサーバーレスフレームワーク等のプラグイン構造・内部契約を模倣する**
  - **不採用理由**: クリーンルームポリシー（[docs/15-clean-room-and-ip-policy.md](../15-clean-room-and-ip-policy.md)）に抵触するリスクが高く、著作権・知的所有権上の課題を生じさせるため。
- **代替案 B: ADRを設けず、PRやコードコメントのみで設計理由を管理する**
  - **不採用理由**: 設計理由や不採用となった代替案のコンテキストが散逸しやすく、長期的なガバナンスおよびコードベースのクリーン性の維持が困難になるため。

## 根拠 (Rationale)

- **クリーンルーム開発の法的・技術的安全性の確保**: 徹底した独立設計により、プロジェクトの知的財産権上の健全性と独立性を保証します。
- **保守性と透明性の向上**: 体系的なアーキテクチャ原則とADRによる決定プロセスの可視化により、新規コントリビューターの参入障壁を下げ、設計のぶれを防ぎます。
- **AWSエコシステムとの互換性**: 公式仕様に準拠することで、AWSの仕様更新や新機能への追従が容易になります。

## 影響 (Consequences)

- **ポジティブな影響 (Positive)**:
  - アーキテクチャの統一感と高いコード品質・設計クオリティが維持される。
  - 設計根拠がADRに蓄積され、過去の決定背景を容易に確認できるようになる。
- **ネガティブな影響・リスク (Negative / Risks)**:
  - 大幅な設計変更時にADRの作成・レビューというプロセスが発生するため、事前検討のコストが必要となる。
- **必要なアクション (Follow-up Actions)**:
  - 今後発生する大きな設計変更（コンパイラ拡張、セキュリティモデル変更等）において、本方針に従って新規ADRを作成・管理する。
